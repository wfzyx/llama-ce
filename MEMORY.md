# Project Memory & Decisions (llama-ce)

*Decisions, architectural patterns, and known quirks for llama-ce. Append-only log: later entries supersede earlier ones; git keeps the history.*

## Bug Fixes & Historical Postmortems

- In repo llama-ce, the tandem.cpp release defaults (lc_apply_release_defaults in common/common.cpp, mirrored in patches/tandemcpp.patch) caused gibberish output on Vulkan with Qwen3.8 Flash-Next (Swift IQ3_S). Official llama gave coherent text. A bisect isolated LLAMA_HC_FUSE=1, which folds the Qwen3.8/DS4 hc scale into the weights. The GDN and conv defaults were cleared. Single-variable runs for LLAMA_PLE_GPU and GGML_SCHED_BATCH_INPUTS were inconclusive. -> Solution: The LLAMA_HC_FUSE default is now 0. The release defaults block is wrapped in #if !defined(GGML_USE_CUDA) && !defined(GGML_USE_HIP), so it is skipped on Vulkan and CPU builds and still applies on CUDA/ROCm. Fix the patch instead of using a LLAMA_MOE_NO_DEFAULTS=1 workaround, per the user's direction. Verified on tower: coherent output with no env overrides, and MTP generation is also coherent. *(Score: 0.95)*
- In repo llama-ce, the toolchain design rules for building llama.cpp, tandem.cpp and selected PRs need to persist across sessions. -> Solution: This is a custom toolchain (llama_ce.py and recipes.toml). It does not use GitHub Actions, self-hosted CI or auto-merged forks. The assistant owns conflict resolution and merge decisions. There is one maintained profile, [profiles.llama-ce]. Other people write their own recipes from README.md and SKILL.md, so do not add more named profiles. Always patch onto current upstream origin/master and never pin an old base commit. patches/tandemcpp.patch is re-ported when conflicts appear. Worktrees prune tests/ (commit 'llama-ce: prune tests') and apply patches with git apply --3way --exclude=tests/*. PR selection: a PR must be READY (not draft) and pass CI. PRs from authors with association MEMBER, CONTRIBUTOR or COLLABORATOR are pulled automatically. Any other PR is pulled only through an explicit 'llama_ce apply <PR#>'. The container is only a compile environment and outputs binaries, not a runtime image. On tower, install llama-ce side by side and never overwrite ~/.local/bin/llama. *(Score: 0.95)*
- In repo llama-ce, builds must be deployed to the tower host (ssh alias tower: AMD RX 7900 XT, Navi 31, 20 GiB VRAM) without disturbing the official Vulkan llama.cpp binary at ~/.local/bin/llama, because the user benchmarks the two against each other. -> Solution: Never overwrite ~/.local/bin/llama on tower. Deploy side by side. The ROCm build lives in ~/llama-ce-rocm/. Its wrapper, ~/.local/bin/llama-ce-rocm, sets LD_LIBRARY_PATH=~/llama-ce-rocm and execs ~/llama-ce-rocm/llama. Confirm the deployment with `llama-ce-rocm cli --list-devices`, which should show ROCm0 AMD Radeon RX 7900 XT (20464 MiB). The user declined a ROCm stage in the llama-ce Containerfile, so the Containerfile supports only cpu, vulkan and cuda. The ROCm build is out-of-band. *(Score: 0.95)*
- In repo llama-ce, the ROCm/HIP build failed in two ways. First, mmvq.cu reported missing host_x/host_gate/host_nb in ggml_cuda_mm_fusion_args_device, along with q8 cache errors, because the tandemcpp additions to ggml-cuda/common.cuh were lost from the work tree. Second, the link failed with an undefined ggml_cuda_moe_fetch_host in libggml-hip.so. -> Solution: Restore the tandem common.cuh additions from patches/tandemcpp.patch: the q8 cache entry struct, the GGML_CUDA_Q8_CACHE_N/SIZE constants, the pack/gather ring fields, the host_x/host_gate/host_nb fields and the ggml_cuda_moe_fetch_host declaration. The link was unblocked with a stub ggml_cuda_moe_fetch_host in ggml-cuda.cu that returns nullptr. That stub is a placeholder, not the real MoE GPU fetch registry. Restore the real implementation from the tandem patch. The work-tree fixes (hc-fused.cu masks, common.cuh restorations, ggml-cuda.cu stub) are not yet captured in patches/tandemcpp.patch. The exported dist/llama-ce-rocm (367 targets) contains the unverified stub. *(Score: 0.95)*
- In repo llama-ce, a ROCm MTP run on tower using tandem release defaults and `-md draft-mtp` hangs. gdb shows cli_server::wait_ready spinning in a nanosleep loop. With LLAMA_GDN_REPLAY=0 LLAMA_MTP_DEFER=0, the run produced no output and timed out after 240 s. -> Solution: Unresolved. Suspect the placeholder ggml_cuda_moe_fetch_host stub (it returns nullptr) before blaming MTP itself. Restore the real tandem implementation, then retest. Always run with an explicit timeout. *(Score: 0.85)*
- In repo llama-ce, a MoE acceleration approach and the set of patches in recipes.toml had to be chosen. -> Solution: The user chose tandemcpp. tandemcpp and BigMoeOnEdge's SSD expert streamer are mutually exclusive: both manage residency of the same ffn_exps buffers, tandemcpp's CPU worker/DMA bypasses BigMoeOnEdge's overlap hook, and their RAM budgets conflict. stew675 rdna-boosts-all.patch (115,620 lines) was rejected because it overlaps tandemcpp and conflicts with origin/master. The recipe stays at tandemcpp, sparse-decode and trusted PRs. *(Score: 0.95)*
